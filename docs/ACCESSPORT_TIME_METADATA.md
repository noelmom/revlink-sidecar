# AccessPort Time Metadata

## What the device provides

Every file entry in an AccessPort `0x1601` directory-listing response contains
an unsigned 32-bit field before the file size. RevLink names this value
`device_time_raw`. The field is preserved exactly as received.

The field does not have one proven meaning across every file type:

- many factory and uploaded map files contain plausible Unix modification
  times;
- locally generated datalogs and screenshots commonly contain smaller,
  counter-like values;
- zero and out-of-range values do not provide usable time information; and
- datalog CSVs contain elapsed `Time (sec)` values, not a wall-clock recording
  start time.

Captured examples include map values that decode to dates in 2021–2023.
Screenshot values sometimes advance like a device counter and can drop after a
reboot. That pattern is consistent with device uptime, but the exact firmware
semantics are not proven.

Map values are more likely to be ordinary filesystem modification times because
the files originate on a tuner workstation. A syntactically valid timestamp is
not necessarily an accurate historical date, however. Legacy tuning workflows
may use virtual machines whose clocks are incorrect or deliberately fixed.
RevLink therefore treats a plausible map value as source metadata, not proof of
when the map was created, edited, or delivered.

## Stored fields

The `files` table stores:

| Field | Meaning |
| --- | --- |
| `initial_sync_at` | RevLink host time when this specific file version was first indexed |
| `device_time_raw` | Exact unsigned 32-bit value received from the AccessPort |
| `device_time_kind` | `unix_mtime`, `device_counter`, or `unknown` |
| `device_time_utc` | ISO 8601 UTC value only when classified as `unix_mtime` |

RevLink uses a deliberately conservative classifier:

- file values from `2000-01-01T00:00:00Z` through, but not including,
  `2100-01-01T00:00:00Z` are treated as plausible Unix modification times;
- smaller positive file values are classified as `device_counter`;
- zero, directories, and values beyond the plausible range are `unknown`.

`device_counter` means only “counter-like device value.” It must not be shown as
a date or described as confirmed uptime.

## Initial sync is separate

`initial_sync_at`, displayed as **Initial sync**, is the time RevLink first
indexed a specific file version. It is generated by the RevLink host and is
never replaced with device metadata. Routine reconnects and incremental syncs
preserve it.

This distinction matters because native datalog rotation can reuse a filename.
When size or the raw device value proves that the content at a path changed,
RevLink assigns the replacement version a new Initial sync. Once bytes are
cached, SHA-256 is the definitive local version identity. RevLink retains the
cached version and its original Initial sync in `file_versions`, even after the
same device path points at newer content.

Existing database rows have `device_time_raw = NULL` after migration. A later
device sync fills the new fields. Existing Initial sync values migrate from
`first_seen`, so user-visible history is preserved without inventing dates.

The ESP32-P4 cache applies the same rule in manifest v2. Its
`initial_sync_utc` value is assigned only when `revlink_time` has a bounded
UTC source. Sources are, in authority order:

1. network time after a successful preferred-network connection;
2. the ESP32-P4 system RTC when it contains a plausible retained value; and
3. the local browser clock, accepted only once while no RTC or network value
   exists.

The browser may seed an offline Direct-mode session, but it cannot overwrite
an existing RTC or network anchor. Network time may supersede the browser
anchor later. Existing manifest-v1 records still migrate with zero rather than
receiving an invented historical date. Once any bounded UTC source becomes
available, RevLink repairs only zero-valued Initial sync fields in the current
manifest and version history for the last unambiguous AccessPort namespace.
This prevents a temporarily offline sync from remaining permanently
**Initial sync unavailable**.

A reconnect that finds the same SHA-256 preserves the original value;
replacement bytes at a rotated filename receive a new one.

### Reset and power-loss behavior

ESP-IDF combines a high-resolution timer with the chip RTC for system time.
The observed Waveshare development board loses that RTC value when a
programming-port reset is reported as a power-on reset and no RTC battery is
installed. Therefore:

- Wi-Fi and browser time close the software gap immediately after boot;
- unknown local records are repaired as soon as either source arrives; and
- accurate unattended timestamps across a complete power loss still require
  the board's supported rechargeable RTC battery.

The final cold-power acceptance test must disconnect external power, wait,
reboot with the RTC battery installed, and prove a plausible retained UTC
value before starting an automatic sync.

### Development cache backfill

On 2026-07-27, at the owner's direction, the ESP32-P4 development card received
a one-time local metadata backfill for the legacy records that predated
manifest v2. RevLink assigned the explicit placeholder
`2026-07-26T19:00:00Z` (July 26, 2026 at 12:00 PM PDT) to 33 zero-valued
current-manifest records and their 33 matching history records. One existing
trusted Initial sync value was preserved. Repeating the operation updated zero
records, proving that the migration was idempotent.

The placeholder is not AccessPort metadata and does not claim to be the files'
recording or creation time. The maintenance operation changed only
zero-valued local metadata on the microSD card; it did not alter cached file
bytes or AccessPort storage. Normal firmware does not expose the maintenance
command. The production runtime uses the same zero-only repair primitive
automatically after acquiring bounded UTC; it cannot rewrite any nonzero
Initial sync value.

The owner later supplied the observed chronological sequence for the current
datalog set: the AccessPort advanced through the available `datalog28.csv`
through `datalog58.csv` records, then wrapped to compressed `datalog1.csv.gz`
and `datalog2.csv.gz`. A second temporary maintenance image assigned those 33
current versions 30-second increments beginning at the same explicit
placeholder. It also updated only the history entries whose path and SHA-256
matched each current version. This matters because a reused filename with
different bytes is a distinct immutable history version and must keep its own
Initial sync value.

After verification, the board was restored to normal firmware with maintenance
commands disabled. The portal's Datalogs view sorts by Initial sync rather than
the numeric suffix, so **Oldest first** begins at `datalog28.csv` and
**Newest first** begins at `datalog2.csv.gz`. The UI explains that AccessPort
datalog names can wrap and be reused.

If a previously tracked non-null device value changes, RevLink treats the file
as potentially replaced and invalidates its cached copy even when the byte size
is unchanged.

## API and UI rules

The file-listing API exposes all three device-time fields. Product surfaces may:

- show `device_time_utc` as **Source modified** when the kind is `unix_mtime`,
  with help text explaining that it reflects the originating system's clock;
- use counter values for engineering diagnostics or relative-order research;
- continue showing **Initial sync** for discovery history.

Product surfaces must not:

- label `device_counter` as a calendar date or confirmed creation time;
- infer an exact datalog recording date from its sequential filename;
- describe **Source modified** as a verified creation, tuning, or delivery date;
- combine the device value with host time and present the result as certain; or
- silently replace Initial sync with device metadata.

## Future validation

To prove stronger semantics, collect controlled observations across reboots:

1. record the raw values for a new datalog and screenshot;
2. wait a measured interval and create another pair;
3. power-cycle the AccessPort and repeat;
4. upload a file with a known modification time and re-list it; and
5. compare multiple firmware and AccessPort generations.

Any stronger interpretation requires capture-backed tests and a documented
firmware scope.
